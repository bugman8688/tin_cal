# ADR-0001：提醒事项只读接入与过期过滤

- 状态：已采纳
- 日期：2026-11-26

## 背景（Context）

面板需要在月历里体现「哪天有没做完的事」。候选数据源有两个方向：自己存一份待办，或接入系统「提醒事项」。

自建待办要额外做增删改查、同步、UI，超出「菜单栏看一眼今天还有什么事」的定位；系统提醒事项已经承载了用户的待办习惯，只读展示即可满足需求。

接入后暴露第二个问题：未完成的提醒会一直挂在过去的日期上，月历上积累大量红点，面板一打开全是旧账，反而看不清今天要做什么。

## 决策（Decision）

**只读接入 EventKit**：只做 `fetchReminders` + 展示，任何编辑 / 完成 / 删除都跳转系统 App。

**过期项一律不展示**，口径固定为：

| 情形 | 处理 |
| --- | --- |
| 到期日早于今天 | 过期，不展示 |
| 到期日为今天且有提醒时刻，当前时刻已过 | 过期，不展示 |
| 到期日为今天且当前分钟恰等于提醒时刻 | **保留**（提醒当分钟仍显示，下一分钟起隐藏） |
| 到期日为今天、无具体时刻（全天） | 保留 |
| 到期日晚于今天 | 保留 |
| 已完成 | 不展示（沿用既有口径） |

**两条出口同源**：底部待办列表与月历灯泡都从 `ReminderStore.remindersByDay` 派生，该属性在读取时按当前时间重算，并用分钟桶缓存保证同一自然分钟内多次访问结果一致。

**完全隐藏**：不提供「查看过期项」入口、不显示过期计数、不做设置开关。

## 备选方案（Alternatives）

1. **在 `fetchReminders` 里一次性过滤并存储结果**
   - 优点：消费方零改动，字典即最终态。
   - 放弃原因：时间推进后不重新抓取就一直是旧快照；叠上 30s 节流，重开面板仍可能显示已过期项。
2. **读取时实时过滤，但两个出口各写一份逻辑**
   - 放弃原因：红点与列表会分叉（红点亮着但点开列表为空），正是本需求要避免的状态。
3. **保留过期项但置灰 / 折叠 / 显示计数**
   - 放弃原因：面板只有 320pt 宽，多一块 UI 就挤压月历；用户明确要求「完全隐藏、不给入口」。
4. **做成设置开关**
   - 放弃原因：自用小工具，固定行为比多一个开关更省心。

## 后果（Consequences）

正面：

- 面板只呈现「今天与未来还要做的事」，过去日期不再有噪音。
- 底部列表与红点结构上同源，不会出现互相矛盾。
- 过期判定是纯函数（`ReminderItem.isExpired`），可直接单测。

代价与边界：

- 面板长时间开着并跨过某条提醒的时刻时，**不会自动消失**——需要下一次交互（点某天、重开面板）触发重算。这是刻意放弃 60s 定时刷新后的取舍：菜单栏面板通常是「打开看一眼就关」。
- 想看历史未完成项，只能去系统「提醒事项」App。
- 判定按分钟粒度，不精确到秒。
- 后续若新增展示出口（如通知、角标数字），必须同样从 `remindersByDay` 派生，不得另起过滤逻辑。
